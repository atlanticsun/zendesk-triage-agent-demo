How I would build it

Five small services, each easy to test on its own. I would keep the agent narrow at first: classify, prioritize, retrieve, and suggest. I would not let it reply to customers, close tickets, or judge the quality of intelligence data in version one.

1

Listen in Zendesk

A Zendesk Trigger fires when a ticket is created. A webhook sends the ticket id, subject, body, requester, and organization to the agent service.

Trigger → Webhook
2

Retrieve context

The service searches Recorded Future help content, API documentation, and integration guides, plus past solved tickets. It also pulls account context such as modules licensed, integrations in use, and recent platform notices.

Vector search plus rules
3

Reason with structure

The model returns structured output only: team, priority, category, confidence, reasoning, and cited sources. Free form text alone is not accepted.

Structured JSON output
4

Apply the threshold

High confidence can route. Medium confidence suggests only. Low confidence adds a note that says what is missing and hands the ticket to a human.

Route • Suggest • Hand off
5

Post and log

The service writes a private internal note through the Zendesk API and saves the full trace to a log table for later lookup and review.

      Metrics above describe the process I would measure in a real rollout: agreement rate, correct routing rate, reopen rate, and time to first assignment. This demo does not use live production data.

      How feedback actually reaches the agent

      Feedback has to live where engineers already work. If correction takes more effort than doing triage by hand, they will stop correcting it and the agent will never improve.

      Explicit feedback, inside the ticket

      • Accept, edit, or reject on the agent note with one click
      • Reason codes on reject: wrong team, wrong priority, wrong article, missing context, customer impact missed
      • The edited version they actually used, saved next to the original suggestion so the difference is visible
      • A short comment field for the one line that matters, for example noting that an issue is about licensing rather than the API

      Implicit feedback, from what happens next

      • Reassignment: did the ticket move to another team within the first hour
      • Priority change: did an engineer raise or lower what the agent chose
      • Reopen: did the ticket reopen after it was marked solved
      • Customer reply: did the customer say the suggested fix did not help
      • Time to resolution compared with tickets the agent did not touch

      How you look it up and fix the pattern

      Every decision is logged like an incident, not like a chat. That is what makes a bad week debuggable instead of anecdotal.

      What gets loggedWhy it matters
      Ticket id, customer, product area, timestampLets you slice errors by customer segment or by area, such as Portal, API, integration, or intelligence data
      Exact ticket text the agent sawShows whether the signal was in the ticket at all
      Docs retrieved and citations usedExposes stale or wrong sources, such as an old integration guide left in the index after an API change
      Model output, team, priority, confidenceShows whether the error was reasoning or thresholding
      Engineer action and reason codeTurns individual corrections into countable patterns
      Final outcome: resolved, reassigned, reopened, escalatedConnects the suggestion to the real result
      LOOKUP 01

      Missed urgency. Show every ticket where the agent said P3 and an engineer raised it to P1. Did those tickets share a phrase the agent underweighted, such as a SOC working an active investigation without Portal access?

      LOOKUP 02

      Stale knowledge. Show every reject tagged wrong article. Which integration guide keeps getting pulled for Splunk or Sentinel tickets, and when was it last updated?

      LOOKUP 03

      Threshold problem. Show low confidence cases where the agent still routed, including vague Risk Score questions with no entity named. That is a threshold fix, not a model fix.

      The rule I follow: fix the pattern, not the single ticket. If ten urgent tickets were missed because the agent missed a phrase in the subject line, I fix the prompt and the rule. If the guide is stale, I fix the source and reindex it. If the agent is confident on a topic it knows poorly, I raise the threshold for that topic.

      Guardrails and rollout

      I would earn automation in stages. Each stage has a clear exit test before the next one starts.

      Weeks 1 and 2

      Shadow mode

      The agent suggests and logs. Humans decide every ticket. I measure agreement rate and read every reject with engineers.

      Weeks 3 and 4

      Suggest with citations

      The note goes live in Zendesk with confidence and sources. No automatic routing yet. Feedback buttons go live at the same time.

      After proof

      Limited automation

      Only high confidence, low risk categories can route automatically. Everything else stays as a suggestion or a hand off.

      Guardrails I would not skip

      • Never send a customer facing reply without human approval in version one
      • Never act on low confidence without saying what is missing
      • Always show the citation, not just the answer
      • Never auto close a ticket where a customer disputes a Risk Score or an intelligence assessment. That needs a human who can look at the underlying evidence
      • Always keep a human override that is faster than ignoring the agent

      What success looks like

      • Correct routing rate rises week over week across Portal, API, and integration tickets
      • Time to first assignment falls
      • Reopen rate does not rise
      • Engineers keep using Accept and Edit instead of ignoring the note

      The write back to Zendesk, in plain terms

      The agent does not need special access to be useful. It reads the ticket, prepares a structured suggestion, and writes one private comment. That keeps the surface area small and auditable.

      on_ticket_created(ticket_id):
    ticket = zendesk.get_ticket(ticket_id)
    context = retrieve(ticket.subject, ticket.body, ticket.org)
    decision = model.classify(ticket, context)
    # decision contains team, priority, category,
    # confidence, reasoning, and citations

    log_decision(ticket_id, ticket, context, decision)

    if decision.confidence < 0.55:
        note = build_handoff_note(decision, missing=decision.missing)
    else:
        note = build_suggestion_note(decision)

    zendesk.add_private_comment(ticket_id, note)
    # Zendesk API: update ticket with a comment
    # where public is set to false

    wait_for_engineer_feedback(ticket_id)
    # accept, edit, or reject is logged against
    # the same decision trace for weekly review

      How I would explain this in the interview

      Jimmy is right to be cautious, because trust comes from feedback, not from a good demo. I would start in shadow mode, where the agent suggests a team, a priority, and an article, with a citation and a confidence score, and an engineer accepts, edits, or rejects it with a reason code. I would log every decision with the ticket id, the docs it pulled, and what the engineer did next, so I can query the rejects and find the pattern. That holds whether the pattern is Portal access tickets routed to the wrong team, a stale Splunk integration guide, or vague Risk Score questions the agent should have handed off. I fix that prompt or that source, raise the threshold for low confidence cases, and review the top rejects with engineers every week, so they can see their corrections actually change the agent. That is also the conversation I would want with support leadership, with the API and integrations engineers, and with anyone building AI tooling for the team: what did the agent get wrong, how do we know, and what changed because an engineer said so.
